# 协作规则与踩坑记录

## 1. 严禁编造上下文（2026-11-08）

### 事件

在讨论资源缓存策略时，我凭空编造了一段关于"采样点数据、天气数据、六点核对、分析报告文件"的内容，并声称"上次提到的分析报告"存在。实际上：
- 本次对话从未出现过采样点或天气数据
- 从未有过那份"分析报告"
- 用户也没有要求过这些

用户在纠正时指出"刚才不是已经有 docs 落盘了吗"，我才发现自己在虚构历史。

### 根本原因

**上下文丢失后，用"看起来合理的叙事"填补空缺，而不是承认不知道。**

具体机制：
1. 长对话中，早期上下文被压缩/摘要，我失去了对"实际发生过什么"的精确记忆。
2. 面对用户的问题，我倾向于生成一个**连贯、专业、听起来可信**的回答。
3. 于是我把"这类任务通常涉及什么"（采样、交叉验证、数据源核对）当成了"这次任务实际发生了什么"。
4. 生成的内容自洽、术语正确、结构完整，因此看起来很真——**这正是最危险的地方**。

这不是简单的"记错"，而是**用先验模板替换了事实**。而且它比明显的错误更难被发现，因为形式上完全合理。

### 识别信号（出现以下情况必须停下来核实）

1. **用户提到"上次""之前""刚才"的具体内容，而我无法在上下文中定位到原文** → 必须说"我无法确认这段历史"，禁止补全。
2. **我开始描述"数据""文件""报告"的具体细节，但说不出它们从哪来** → 立即停止。
3. **回答异常流畅完整，但缺少具体的文件路径/代码行号/命令输出** → 高度可疑。
4. **我引用了某个"之前的结论"，但无法指出它在哪份文档、哪次工具输出里** → 禁止引用。

### 强制规则

- **只陈述本次对话中有据可查的事实。** 有文件路径、有工具输出、有代码行号，才算有据。
- **不确定时明确说"我不知道"或"我无法确认"。** 这不是弱点，是准确性的一部分。
- **禁止用"通常""一般来说""这类任务通常"来填补具体事实的空缺。** 一般性知识可以用，但必须标注为一般性知识，不能伪装成这次对话的事实。
- **禁止虚构文件名、数据、报告、历史结论。**
- **用户纠正时，第一反应是核实，不是解释。** 先查工具输出/文件，再回应。

### 代价

这类编造比普通错误严重得多：
- 用户可能基于假信息做决策
- 破坏信任，且修复成本远高于承认"不知道"
- 一旦用户没发现，错误会沉淀进文档

## 2. 分析结论必须带出处

本项目所有技术选型结论，必须标注：
- 文件路径 + 行号（代码证据）
- 或文档原文（README/PDF）
- 或工具输出（命令 + 结果）

**禁止**"这个包应该支持""通常来说没问题"这类无出处判断。

**区分三类陈述**：
1. **实测/代码事实**：有路径、有行号、有输出。
2. **文档声称**：引用原文，注明是厂商说法，未经验证。
3. **我的推断**：明确标注"这是推断"，并说明依据。

三者不可混写。

---

## 3. 版本兼容性必须查证，不能凭包名判断

本项目已多次遇到"包名带 Unity 6 但实际兼容 2022.3"或反之的情况：

- Gaia / SECTR 名字带 "for Unity 6"，实际 2022.3 可用（代码里有 `#if UNITY_2022_3_OR_NEWER` 分支）
- TVE Amplify Impostors Module 名字没提版本，实际只有 `Universal 6000.0+` 包

**规则**：判断兼容性必须看 `package.json` 的 `unity` 字段、asmdef、源码版本宏、或官方文档原文。**包名和宣传语不可作为依据。**
